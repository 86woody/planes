# T070 checkpoint: Copilot CLI adapter

## What works

- `mc-hook copilot-cli <Event>`: stdin JSON (snake_case or camelCase) -> Claude Code event names,
  same allowlist as ingest.md 4; `source: new` -> `startup`, `agent_idle` -> `idle_prompt`.
- Agent PID rule `copilot`; reducer and summaries treat `copilot-cli` like `claude-code` (SM-39).
- `mc install copilot` / `mc uninstall copilot` (+ `--dry-run`): owns
  `<COPILOT_HOME or ~/.copilot>/hooks/mission-control.json`; backup, atomic write, idempotent,
  refuses malformed or non-v1 files, manifest key `copilot-cli`, uninstall removes only its entries.
- CP-01..CP-14 pass. Design in D-36; contract text in ingest.md 6.3, attention.md SM-39, USER-GUIDE.

## What is unconfirmed (docs do not say; confirm in the real run)

- That 1.0.83 delivers the payload on stdin to an `exec` hook (use-hooks doc says stdin; the reference page does not).
- Whether PascalCase payloads carry `hook_event_name` (the hook takes the event from argv, so it does not matter).
- `permissionRequest` payload fields beyond `toolName`/`toolInput`; the `Notification` types in practice.
- That `copilot` is the direct parent of the hook process on Windows (agent rule falls back to null).
- That an empty stdout and exit 0 from a PermissionRequest hook leaves approval to the user.

  copilot fixtures do not feed the Claude tests.
