## Deviations and judgment calls

- Fixtures are loaded with JSON import attributes (`with { type: "json" }`), not `fs`.
  The task says "read with fs", but `eslint.config.js` bans `node:*` imports in
  `packages/core/**` and that config is frozen. Lint had to pass, so I used JSON imports.
  Only two fixtures are imported (needs_permission, needs_input).
- `decideRenotify` returns `disabled` when `config.enabled` is false. attention.md
  NP-11 does not list `enabled`; I added it so a disabled config never renotifies.
- `decideRenotify` returns `ended` for ended/lost sessions. NP-11 does not list this;
  added as a defensive guard.
- `decide` and `decideRenotify` treat `attention.active` with `reason === null` as
  `no_change`. The schema allows it, the contract does not say what to do.
- Quiet-hours range with start === end is treated as empty (never quiet).
- Coalescer windows are fixed, not sliding: a window opens at the first offer after
  the previous window closed, and is closed once `now >= start + 5000`. The task said
  "rolling" but also `windowStart`, and NP-12's expected flush(5000) only works with
  a window starting at t=0.
- The summary body uses the held count literally ("N sessions need attention"), so
  it reads "1 sessions" when one is held. The contract wording was kept as written.
- Held notifications that close in a window the caller did not flush are queued and
  returned by the next `flush` (one summary per window).

## What does not

- Nothing known broken. Renotify and the coalescer are only covered by unit tests with
  fixed timestamps; no caller exists yet to exercise them.

## What surprised me

- The eslint rule means core cannot read fixtures via `fs` at all, which the task text
  did not anticipate.
- `dedupe` is used for renotify when the interval has not elapsed, since the
  `why` union has no better fit.
