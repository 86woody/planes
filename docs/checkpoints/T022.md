# T022 checkpoint: VS Code bridge registry (daemon side)

## What works

- `createBridgeRegistry` in `packages/daemon/src/bridge.ts` implements `attach`, `windows`,
  `findForSession`, `request`, `rebind`, `onChange`, `close` from `internal.md`.
- `attach`: 5 s hello deadline (1008), JSON and schema validation via
  `validateBridgeClientMessage` (1008 on failure), `hello` replies `welcome`,
  `terminals` replaces the list, `windowState` updates focus and schedules binding,
  `result` resolves the pending request. Close removes the window and rejects its
  pending requests with `disconnected`.
- Binding: 150 ms after a focused `hello` or `windowState`, reads
  `platform.foregroundWindow()`; binds only when the app (lower-cased, `.exe` stripped)
  is in `VSCODE_NAMES`, and clears the same handle from every other window.
- `request`: `r-<n>` ids, 2000 ms timeout, `no_window` for unknown windows.
- Tests BR-01..BR-08 in `packages/daemon/test/bridge.test.ts` (fake socket, FakePlatform
  with `foregroundWindow` spied, fake timers throughout).

## Judgment calls (not spelled out in the task)

- A non-`hello` message before `hello` closes 1008 ("expected hello").
- A second `hello` on an already-registered socket closes 1008 ("duplicate hello").
- A `hello` for an existing `windowId` replaces the entry but keeps its `nativeWindow`
  binding. The old socket's later close is ignored because the entry now points at the new socket.
- `findForSession` iterates ancestry nearest first, then windows; the first pid hit wins.
- `request` resolves `send_failed` if `socket.send` throws (not in the spec).
- `rebind(windowId, null)` clears the binding; `rebind` with a handle also clears that
  handle from other windows, as binding does.
- `close()` closes all tracked sockets with 1001 and rejects pending requests.
- `clock` is used only to stamp `boundAt`.

## Surprises

- `FakePlatform.foregroundWindow` reports app `FakeTerm`, so BR-04 and BR-05 spy on it
  to return `Code.exe` and `chrome.exe`.
