## Deviations from the literal steps (please review)

1. **Fake platform liveness (step 1.4).** `FakePlatform.processAlive` reports every pid alive by
   default, so IT-05 and PS-05 could never end a session. `DaemonFakePlatform` in main.ts keeps the
   fake's recorded call and ANDs it with the real `processAlive` from `@mc/platform`. Only used with
   MC_PLATFORM=fake.
2. **Fake platform construction.** For MC_PLATFORM=fake, main.ts builds the fake directly so it can
   append every FakeCall to `fake-platform.jsonl`. `createPlatform` is used for every other platform.
3. **displayEnv.** Built from `{...process.env, ...env}` (the startDaemon env param wins), so an
   in-process caller's MC_PLATFORM is seen by `createPlatform`. Display keys are filled from the
   newest record with them, only for keys the base lacks (step 1.4).
4. **BG-01 measures a daemon process, not the vitest worker.** Step 4 measured
   `process.memoryUsage().rss` in-process. Measured that way, the vitest worker alone is about 101 MB
   before the daemon starts, and the load takes it to 153 to 161 MB (heapUsed was about 25 MB; forcing
   GC did not change RSS). The assertion therefore measured the harness, not the daemon. BG-01 now
   starts `packages/daemon/dist/bin.js` as a child process and reads its RSS from the OS (PowerShell
   WorkingSet64 on Windows, `ps` elsewhere). AC-20 is about the daemon's own RSS.
5. **Test env for in-process daemons.** `registerTest` (routes/test.ts, T026) reads
   `process.env.MC_PLATFORM` and the caller's testMode, not the startDaemon env, so the harness sets
   process.env.MC_PLATFORM=fake and MC_TEST=1 for the test file and restores them afterwards.
6. **Deterministic hook.** `runHook` spawns the hook with a minimal child env (no WT_SESSION,
   TERM_PROGRAM and similar) from a temp cwd outside any git repo, so the envelope and project name do not
   depend on the checkout state or the shell. IT-03 writes `config.json` with a closed port so a
   spooled hook can never reach a real daemon on 47800.
