# T084 checkpoint: repair in place (claude-code, copilot, codex)

## What works

- `claude.ts`: `isMcClaude` identification; install walks each event, repairs the first mc
  object in place (type, command, args, async, timeout; key order kept), removes later
  duplicates and emptied groups, and writes once with a backup. `uri-handler` step prints
  `uri-handler skipped (MC_HOME set)` when MC_HOME is set on win32/linux. Uninstall scans
  every key of `settings.hooks` and removes every `isMcClaude` object.
- `copilot.ts`: `isMcCopilot(h, event)`; the same walk over the flat `hooks[event]` list;
  uninstall scans every key of `root.hooks`.
- `codex.ts`: `isMcNotify(argv)`; an mc notify line is rewritten in place with its
  `--chain` kept and is never wrapped; an already-correct line prints
  `codex: notify already installed` and exits 0. Manifest keeps `original` and `eol` only
  when the previous entry had them. Uninstall finds the first `notify =` line, parses it,
  and restores the recorded original when it matches the rule.
- `prepareLaunchers(ctx)` is called before the first write in all three installers; the
  helper skips it on dry-run.
- `packages/cli/test/install-repair.test.ts`: RP-01 to RP-14 with the exact titles from
  the task file, all passing.

## What does not

- Nothing known to fail. Typecheck and lint pass.

## Notes and surprises

- Codex calls `prepareLaunchers` before the already-installed early return, so launchers
  are refreshed even when the notify line is unchanged. The task text says "once validation
  has passed", which this matches.
- Codex uninstall searches for the first `notify =` line anywhere in the file, as the task
  specifies, not only before the first table. This is looser than install, which only looks
  at top-level lines.
- The claude-code install output for a changed file is now
  `added A hook group(s), repaired R, removed D duplicate(s) in <file>`. The existing T051
  tests still pass with this text.
