# T053 checkpoint: shell integration snippets

## What works
- `packages/cli/assets/shell/mc.bash`, `mc.zsh`, `mc.ps1`: prompt hooks that send
  ShellStart, ShellCommandStart (first word only), ShellCommandEnd (exit code, duration ms),
  ShellPrompt and ShellExit through `mc-hook shell`. Hook calls are backgrounded and silent
  (bash/zsh `( ... & )`, pwsh `Process::Start` with redirected output, never waited on).
- Each snippet reads `MC_NODE` and `MC_HOOK_JS` from the env file and does nothing when
  either is empty or the hook file is missing.
- `packages/cli/test/shell-integration.test.ts`: SH-01..SH-05, 5/5 pass, from Git Bash and
  from Windows PowerShell (`powershell -NoProfile -Command "pnpm task:check T053"`).
- Lint and typecheck green.

## Attempt 2: bash resolution on win32
- Attempt 1 picked `bash` by PATH order. From PowerShell that is `C:\WINDOWS\system32\bash.exe`
  (the WSL launcher), so SH-01, SH-02 and SH-05 failed (`/bin/bash: line 1: : No such file`).
- Fix: on win32 the test resolves Git for Windows bash explicitly. It takes
  `<git root>\bin\bash.exe` from `where git`, falls back to `C:\Program Files\Git\bin\bash.exe`,
  and never accepts a path under System32 or WindowsApps. Its `usr\bin` is put first on PATH
  so `sh` and `sleep` resolve. Bash-facing paths are `/c/...` (`bashPath`); env-file paths
  stay `C:/...` because pwsh reads the same file.
- `which` is absent from PowerShell, so the helper uses `where` on win32. zsh and pwsh are
  spawned by name (Node cannot spawn the extensionless path that `which` returns).
- If no Git Bash is found, the bash tests assert that the resolver returned null and return.

## What does not work or is unverified
- zsh is not installed on this machine. SH-03 only asserts `which zsh` is null, as the
  task specifies. The zsh snippet is not exercised by any run; treat it as unverified.
- The pwsh PSReadLine Enter handler (ShellCommandStart/End from typed commands) needs an
  interactive host. SH-04 covers ShellStart, ShellPrompt and prompt preservation only.
- bash: the test drives `PROMPT_COMMAND` by hand (`eval "$PROMPT_COMMAND"`) because a
  non-interactive `bash -c` never runs it. The DEBUG trap and the prompt hook are real.

## Decisions and surprises
- Env file location: the snippets read `${MC_SHELL_ENV:-__MC_STATE_DIR__/shell.env}`
  (pwsh: `$env:MC_SHELL_ENV`). The installer (T051) is expected to replace
  `__MC_STATE_DIR__` with `<stateDir>`. The task file does not name the mechanism, so I
  chose this. T051 must agree with it. Unsubstituted, the placeholder path does not exist
  and the snippet is a no-op.
- bash and zsh `trap ... EXIT` replace any existing EXIT trap of the user. pwsh uses
  `Register-EngineEvent` and does not clash.
- pwsh's Enter binding is replaced by a handler that calls AcceptLine after reporting;
  a user's own Enter binding is overridden.
- Event ordering: hook processes are launched in order but can finish out of order. The
  test sorts by hook process start time (ingest.md 3) and only asserts order for events
  separated by 300 ms, so it is not flaky on jitter.
