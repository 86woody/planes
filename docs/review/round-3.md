# Review round 3

Reviewer: adversarial reviewer (Claude). Date: 2026-11-11. Scope: only the draft D-21
("Answer from the notification", milestone M6). No other file was edited. I read the probe
logs (`events.jsonl`, 54 lines; `answer-events.jsonl`, 20 lines; `answer.js`, both
settings files) and fetched the first 100 000 of 293 000 characters of
code.claude.com/docs/en/hooks.md. The PermissionRequest section itself was not in that
excerpt, so the `decision` fields, `updatedInput` and `interrupt` are unconfirmed by docs.

## Verdict: CHANGES REQUESTED

The idea is sound and fail-open is the right default. But the security design depends on a
field that does not exist (`tool_use_id` on PermissionRequest), the central probe claims
are narrower than stated, and the Allow/Deny path (the dangerous half) has not been probed
at all. No task should be written from D-21 yet.

## Probe claims, checked

- Q1 (PreToolUse and PermissionRequest both fire for AskUserQuestion, about 90 ms apart): supported in all six runs.
- Q2: supported for a hook answer (three runs); typed Other supported only from the terminal path.
- Q3: partly supported (one run). See F-3-02.
- Q4: supported as to type `permission_prompt`; ordering claim conditional.
- Q5: nothing was learned; the probe used 90 s and 10 s settings, never 600.

## Checked and found sound

- Fail-open intent (daemon down, error or timeout: exit 0, no decision) is consistent with the docs: exit 2 is ignored on PermissionRequest and a timeout discards output.
- No `updatedPermissions` in v1, so no standing rule from a click.
- Default-off flag plus browser-only fallback is the right shape.
- Rejecting SendKeys is consistent with the PRD.
- Per-OS limit "Other is page-only on Linux and macOS" has no contradiction with the capability matrix.

## Stance

Not AGREE. Fixes F-3-01 to F-3-06 are needed before a task is written; the rest can be
settled in the same pass.
