# T015 checkpoint

## What works
- `packages/daemon/src/auth.ts`: `createAuth(paths, clock)`.
  - Token file: 32 random bytes as base64url (43 chars), created with mode 0600 (`wx` flag), then `icacls /inheritance:r /grant:r <user>:F` via `execFile` on Windows.
  - Pair codes: 8 Crockford characters shown as `XXXX-XXXX`, one live code at a time, 60 s expiry, single use, dropped after 5 wrong attempts. Input is trimmed, upper-cased, dash removed.
  - Browser sessions: cookie is 32 random bytes (base64url). Only `sha256(cookie)` is kept, in `stateDir/browser-sessions.json` as `[{cookieSha256, lastSeen}]`. The file is written atomically (temp + rename, mode 0600, same icacls step on Windows) on pair, on expiry removal, at most once per 60 s for `lastSeen`, and in `flush()`. Sessions expire after 30 days idle.
  - CSRF is derived: `base64url(HMAC-SHA256(key = token, msg = cookie))`. `csrfFor` returns it for a live session. Digest and HMAC comparisons use `timingSafeEqual`.
- `packages/daemon/src/security.ts`: `registerSecurity(app, {port, auth, testMode})`, `onRequest` in api.md 1 order: Host (421), OPTIONS (405, no CORS), realm (401 no credential, 403 bad credential, Origin rules), body size (413), rate limit (429). `onSend` adds `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` to every response, and the CSP to `text/html`.
- `packages/daemon/test/security.test.ts`: SEC-01..SEC-15 with the exact titles. Each test uses a temp dir and port 0.
- Acceptance: `pnpm task:check T015` prints `TASK T015 PASS 15/15`, exit 0. `pnpm -w run typecheck` and `pnpm -w run lint` exit 0.

## What does not / unverified
- The 413 path is only partly exercised. The content-length check runs in `onRequest`, and `registerSecurity` also sets Fastify's `bodyLimit` per route in an `onRoute` hook so chunked bodies are cut off. No test covers 413 or the `onRoute` path; it is untested in the suite.
- The Windows icacls step: SEC-10 passes on Windows. It asserts the icacls output has no `BUILTIN\Users` or `Everyone` entry. That only passes if icacls succeeded, and I saw no failure. If icacls fails in production, the failure is swallowed silently.
- Only `src` is covered by typecheck (`tsconfig` includes `src` only); the test file is checked by vitest alone.

## Decisions for the orchestrator and later tasks
- Route config rate limit: I added an optional `windowMs` (default 1000) to `rateLimit`. api.md 4 says "pair: 10 per minute", and the task's config shape `{perSession?, total}` has no window, so the pair route (T026) must set `rateLimit: {total: 10, windowMs: 60000}`. Otherwise it silently becomes "10 per second".
- Route config also takes optional `allowedOrigins` (used by `/bridge/v1`), as the task asked.
- Error codes: the `Error.code` enum has no code for 405 or 413, so OPTIONS and oversize bodies return `invalid_request`.
- `HEAD` is treated as a safe method next to `GET`, so it needs no CSRF header. api.md only names GET.
- Browser-realm Origin check is applied only when an Origin header is present, as api.md 2 says. `POST /api/pair` (realm `none`, Origin must be the daemon's) is a route-level check for T026 and is not in this module.
- `lastSeen` is written at most every 60 s; a dirty state not yet written at shutdown is covered by `flush()`.
- The cookie name `mc_session` is a constant local to `security.ts`. T026 sets `Set-Cookie` with the same name.

## What surprised me
- `checkBrowser` needs no CSRF for GET or HEAD (api.md 2 names only GET). SEC-13 and SEC-15 call it with POST and a matching CSRF.
- The token file has to be read with `trim()`. A trailing newline added by an editor would otherwise change the HMAC key and fail every CSRF check. Writes never add one.
